# Development

Hotori uses Rust and Tauri 2 with a local HTML/CSS/JavaScript interface. Build on Windows with Rust/MSVC and Microsoft C++ Build Tools. Running the app requires Microsoft Edge WebView2 Runtime.

## Build and test

```powershell
cargo build --release --locked
cargo test --release --locked
```

Keep updating the main executable at `target/release/hotori.exe`; do not generate separate versioned preview EXEs unless the user asks for them. Use `cargo run` for development. No frontend bundler is required.

The optional native UI tests use Playwright and a disposable AppData folder:

```powershell
npm install
npm run test:native
```

Fully quit Discord (including its tray process) before running native installation tests: automatic theme activation requires Vencord to be closed. These tests exercise the release EXE without changing your installed Vencord themes. Screenshots and temporary profiles are stored in `target/qa`.

## Publishing theme updates

For Discord updates that rename generated CSS classes, follow [the theme compatibility recovery workflow](theme-compatibility.md). It includes snapshot capture, a read-only mapping report tool, review requirements and the November 6, 2026 migration record.

Every theme release must update **both** `assets/hotori.theme.css` and `assets/theme-changelog.json` in the same push. Add short, user-facing notes under the exact new theme version. Run `cargo test --release --locked theme_changelog::tests` before publishing theme changes. The app reads this catalog from the default branch independently of app releases; do not substitute app release notes for theme notes.

Run `python scripts/check-theme-changelog.py` before pushing theme changes. The **Theme release notes** GitHub Actions check runs the same validation on pushes and pull requests, reporting a failure if the current theme version has no notes. This check reports problems; preventing direct pushes requires branch protection configured separately.

Update `assets/hotori.theme.css` in this repository. Keep the name `Hotori`, bump `@version`, retain exactly one `END OF USER SETTINGS` marker, and keep each user-setting declaration on its own line.

The app's theme update notice fetches this file from the repository's default branch when clicked. Existing values in the user-settings section are preserved when their variables still exist in the new theme. New variables use published defaults; removed variables disappear with the old implementation. Metadata and implementation come from the published file. Downloads are limited to 2 MB with a 30-second timeout; invalid downloads and detected concurrent edits abort the update.

The installed theme is `%APPDATA%/Vencord/themes/hotori.theme.css`. The published source is cached in `themes/hotori-assets/theme-defaults.css` for Reset to defaults and slider bounds. Bundled defaults are the offline fallback. Local wallpapers are copied into `themes/hotori-assets` and referenced through Vencord's local theme protocol.

Theme updates and EXE releases are independent. Attach `hotori.exe` to app releases; keep build outputs out of Git. Push only when explicitly requested.

## App versioning

Small fixes increment the patch version by 0.0.1 (for example, 1.0.0 → 1.0.1). Larger features use a minor bump; major changes may warrant a major bump. Keep Cargo.toml, the Hotori entry in Cargo.lock, tauri.conf.json, and the visible version label in web/index.html aligned. Theme versions are independent of app versions.

Version components are independent integers, not decimal digits. Patch versions continue from **1.6.9 → 1.6.10 → 1.6.11**; reaching 9 does not trigger a minor-version bump. Minor and major bumps depend on the scope of the change.

Build and verify the local EXE first. Wait for the user's verification and explicit publishing instruction before pushing or changing GitHub releases.

## Signed portable app updates

Hotori 1.1.0 adds **Update Hotori**, separate from **Update theme**. It checks the latest stable GitHub release, offers Download & restart, verifies an Ed25519-signed manifest and the EXE's SHA-256/size, then stages the app beside the running EXE. A copy of the current app acts as the temporary helper. It waits for the original process to exit, keeps a backup while replacing the EXE, and restores the old version if the new app fails its startup acknowledgement. Paths containing spaces are supported. Theme files and wallpapers are not involved in app replacement. The EXE's folder must be writable.

Prepare an app release locally on the signing Windows account:

```powershell
cargo build --release --locked
python scripts/sign-release.py sign
```

The Python signing tool requires `cryptography`. Its default EXE is `target/release/hotori.exe`; it verifies the Windows product version against `tauri.conf.json` before signing. After user approval, attach these three files to the matching stable `vX.Y.Z` GitHub release:

- `hotori.exe`
- `hotori-update.json`
- `hotori-update.json.sig`

The app embeds only `assets/update-public-key.hex`. The private key is Windows-DPAPI protected at `%LOCALAPPDATA%/Hotori/signing/update-key.dpapi`, outside this repository. Keep this key and its Windows account available for future releases. Do not regenerate the public key for an existing app: old copies trust the original key. A lost signing key requires users to download a new trusted app manually. These update signatures verify app downloads; they are separate from Windows Authenticode signing.

The 1.0.0 release predates app updates. Users on that version must manually download their first updater-capable EXE; signed releases from 1.1.0 onward can be installed from inside the app. No update is downloaded automatically on startup. No push or GitHub release is performed by the signing script.

`node tests/app-update-smoke.cjs` performs a real replacement/restart using disposable EXE copies and the locally signed release artifacts. It builds an older-version helper harness under `target/qa`, checks paths with spaces, verifies the real new app starts, and confirms user theme/wallpaper files survive. `HOTORI_TEST_APP_UPDATE=1` additionally enables a live GitHub app-update check in the native smoke test.

The 1.7.4 release assets were refreshed at the user’s request without a version bump: startup offers available app updates in the existing liquid-glass dialog after wallpaper/window readiness, waits for active operations/dialogs, and stays quiet offline or when up to date. Versions are bold within subtle Inter supporting copy; Not now/Escape dismiss the offer for this launch. No automatic download occurs. Existing 1.7.4 installations need to download the refreshed EXE manually because version-based updates do not detect same-version replacements.

The installation guide now covers category saves/drafts, wallpaper crop and preview differences, app-only overlay brightness, recommended color autosaves and notification dots, Friends Sidebar controls and theme requirement, separate theme/app updates with the startup prompt, and reset/uninstall confirmations. Version 1.7.5 publishes the expanded guide and includes the startup update prompt for users upgrading from the original 1.7.4 build. Resume normal patch increments for subsequent fixes; the earlier same-release exception no longer applies.

### Performance regression workload

Run `npm run test:performance` for deterministic counters and comparative scrolling timings. `node tests/performance.cjs --label baseline --ref 540c444` serves frozen 1.8.0 sources for comparison. Measurements are headless/local rather than universal FPS guarantees; idle phases must have zero uploads, DOM captures, and PNG encodes. Scrolling must not encode control PNGs or capture empty setting-row wrappers. The performance harness includes an invisible animated skeleton to catch accidental perpetual render loops.

The final local 1600×900 stress run recorded settings-scroll p95 frame time of 8.7 ms versus 175 ms for published 1.8.0, with 0 versus 14 long tasks. These are comparative headless measurements, not guaranteed frame rates on every machine. Ordinary wheel input uses passive observation unless Ctrl zoom is active. Crop preview redraws are coalesced to one per animation frame, preview style updates skip unchanged values, and native crop canvas pixels are composed directly rather than serialized through DOM snapshots.

Message bubbles controls live under Messages → Message bubbles. The Off/On choice maps to 0/1; Your Messages and Other Messages always expose color and opacity controls. Requires the user to enable Vencord’s built-in ThemeAttributes plugin manually under Discord Settings → Vencord → Plugins → ThemeAttributes. The installer does not change plugin settings. Color validation accepts hex (including alpha) and bounded RGBA, including palette/recommendation saves. Saved bubble values survive updates; missing values use the published source defaults and reset restores those defaults. The local 0.9.4 theme retains its single group-wide backdrop and defaults to Off; DEV remains On.

Wallpaper responsiveness: display previews use bounded PNG blob images (up to 2048 pixels wide), while crop inputs/exports keep the original pixels. Overlapping app lenses sample the illustration wallpaper directly rather than serializing the full miniature Discord DOM; the visible miniature UI remains native and unchanged. The sampled backdrop omits miniature labels and panels. Preview-only snapshot resolution is capped independently of the original asset. `node tests/performance.cjs --wallpapers` exercises actual wheel scrolling over a preview; an optional `--wallpaper-image PATH` uses a local JPEG fixture. No personal fixture paths are committed.

Home Logo: Server List → Home Logo imports original local PNG/JPEG/WebP/GIF bytes through the existing wallpaper asset store into hotori-assets. The separate --home-logo image field serializes supported local URIs as url(...); Clear serializes none. Original images are retained locally with crop metadata for Crop & zoom; Cancel imports nothing. The selected square copies source pixels 1:1 without interpolation or upscaling and retains transparency. The result preview uses contain. Transparent artwork is recommended. Pending theme CSS remains unchanged and unpublished, with its own version independent of installer 1.8.5.

Validation accepts only finite percentages within 0–50, preserves unchanged values, and leaves --avatar-radius independent. Theme CSS and DEV artwork/defaults are not changed by installer development.
